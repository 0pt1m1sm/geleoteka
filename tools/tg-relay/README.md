# tg-relay — прокси к Telegram Bot API вне РФ

Часть проекта Geleoteka. Крутится на **Railway** (проект `tg-relay`, сервис
`tg-relay`, env `production`), домен `tg-relay-production-013b.up.railway.app`.
Это единственное, что у нас осталось на Railway — **не удалять**: без него
уведомления сотрудников в Telegram из прод-контейнера Timeweb (РФ) перемежаются
таймаутами (РКН). Почему релей и как он используется — `docs/runbooks/staff-notifications.md`.

**`server.js` здесь — дословный исходник того, что реально работает в бою**
(снят с контейнера `railway ssh cat /app/server.js` 2026-08-30 и сверен).
Не «улучшайте» его мимоходом: см. раздел о возможных доработках ниже.

## Как это работает

Приложение хранит в настройке `TELEGRAM_API_BASE_URL` (админка → интеграции)
адрес `https://<домен-релея>/<RELAY_KEY>` и шлёт `${base}/bot<token>/<method>`.
Релей проверяет префикс `/<RELAY_KEY>/`, отрезает его и пересылает запрос на
`https://api.telegram.org`. Путь без ключа → `404` без тела. Ошибка апстрима →
`502` без тела: любая деталь здесь потенциально содержит URL с токеном.

Никаких зависимостей — `node:http` + встроенный `fetch`, CommonJS. **Ничего не
логируется вообще**, даже старт: в пути каждого запроса лежит токен бота,
поэтому логирование запросов запрещено и в коде, и в настройках Railway.
Таймаут на апстрим сознательно не ставится — длинный опрос `getUpdates` висит
до ~25–30 секунд и должен проходить насквозь.

## Переменные сервиса (Railway → Variables)

| Переменная | Назначение |
|---|---|
| `RELAY_KEY` | Секретный префикс пути. Обязателен, без него процесс не стартует. Тот же, что в `TELEGRAM_API_BASE_URL` приложения. |
| `PORT` | Задаёт Railway. |

## Доступ и деплой

```bash
railway login                                          # интерактивно, нужен настоящий терминал (не из Claude Code)
railway link -p tg-relay && railway service tg-relay   # привязка каталога (один раз на машину)
railway status / railway variables / railway logs / railway deployment list
```

Сессия CLI протухает — если команды отвечают `Unauthorized`, нужен повторный
`railway login` в обычном окне терминала.

Деплой — **только из этого каталога**, чтобы в архив не попал весь монорепо:

```bash
cd tools/tg-relay && railway up --service tg-relay
```

Смена `RELAY_KEY` = одновременно поменять `TELEGRAM_API_BASE_URL` в админке.

Healthcheck в `railway.toml` намеренно не задан: отдельного эндпоинта состояния
у релея нет, любой путь без секретного префикса отдаёт 404 — healthcheck по
нему валил бы деплой.

## Проверено

Локальный смоук дословного исходника против мок-апстрима: 404 без префикса и с
чужим префиксом, проброс метода/тела/query, проброс статуса 400 от апстрима,
502 при недоступном апстриме, пустой лог, отказ старта без `RELAY_KEY`.

## CodeQL: `js/request-forgery` — снят как ложное срабатывание

Сканер помечает `fetch(upstreamUrl)` критическим SSRF: URL строится из
пользовательского пути. Для прокси это неизбежно по определению, а хост здесь
прибит константой `UPSTREAM` — управлять адресатом клиент не может.

Проверено эмпирически (два мока: «телеграм» и «злоумышленник»; во всех случаях
запрос уходил на первый): `../..`, `//host:port/x`, `@host:port/x`,
percent-encoded `%2e%2e%2f`, обратные слэши `\..\host`. Absolute-form
(`GET http://evil/x HTTP/1.1`) не начинается с секретного префикса и отвергается
404. Повторить: см. историю сессии 2026-08-30 / PR #95.

Что атакующий со знанием `RELAY_KEY` действительно может — гонять произвольные
вызовы Bot API через наш выход. Это ровно назначение релея, и защищает от этого
секретность префикса, а не сканер.

Если правку сюда всё же понадобится внести — не глушите алерт комментарием в
коде: файл обязан оставаться дословной копией прода.

## Возможные доработки (НЕ применены, в бою их нет)

При восстановлении исходника была написана более «правильная» версия прокси;
от неё сознательно отказались в пользу дословного совпадения с продом. Если
когда-нибудь понадобится, вот чего в текущем релее нет:

- проброс **всех** заголовков в обе стороны (сейчас только `content-type`);
- потоковая передача ответа вместо буферизации целиком (важно только для
  больших файлов, которых у нас нет);
- graceful shutdown по `SIGTERM`;
- эндпоинт `/healthz` (и тогда healthcheck в `railway.toml`);
- явный таймаут на апстрим — **осторожно**: он обязан быть заметно больше
  длинного опроса (`TELEGRAM_POLL_LONG_POLL_SECONDS = 25`), иначе релей начнёт
  рвать штатные `getUpdates`.

Любую из них — только отдельным изменением с передеплоем и проверкой приёма
сообщений, а не «заодно».
