# Чего нет у нас из того, что есть у Bazon

Created: 2026-09-01

Agent: Claude Code

## Постановка задачи

Bazon — отраслевая CRM для автосервисов и продажи запчастей. Разбор их функциональности
показал набор возможностей, которых у нас нет. Владелец решил: закрыть пробелы, чтобы у нас
было.

Важно, что именно закрывать. Bazon — коробка для рынка РФ: сервис покупает у российских
поставщиков (Emex, Autopiter, Berg) и продаёт в розницу. У нас другая экономика: **закупка за
границей партиями, продажа с наценкой**, плюс б/у детали, снятые с машин. Поэтому пункты их
списка переносятся не один в один: часть бесполезна, часть нужна в другой форме, а часть — то,
без чего магазин просто не работает.

## Продуктовый контур

Мы строим **не сайт автосервиса, а продукт для автосервисов**. Гелеотека — первый боевой
клиент, на котором обкатывается платформа: «продал легаси-сервису — у него сразу появилось
много возможностей». Отсюда правило для всего, что ниже: возможность делается универсальной,
настройки живут данными тенанта, а не в коде.

Практически это значит: ни адреса, ни реквизитов, ни ключей эквайринга, ни номера телефона,
ни названия сервиса в коде быть не должно — всё через настройки. Часть уже так и устроена
(CMS, `lib/settings.ts`), часть — нет.

Изоляция арендаторов при этом **ещё не сделана**: `lib/tenant.ts` — это константа
`TENANT_KEY = "geleoteka"`, `tenantKey` расставлен по части моделей со значением по умолчанию.
Целевая модель и цена разобраны в `docs/plans/2026-07-31-multi-tenant-platform.md` (144–210
инженерных дней, три варианта объёма, решение за владельцем, ещё не принято). Каждая
спецификация ниже говорит, что в ней меняется от мультиарендности и что придётся переделывать,
если изоляцию отложить.

## Что проверено, а не предположено

Каждый пункт сверен по нашему коду, а не по памяти. Итог сверки:

| Возможность Bazon | У нас | Проверено |
|---|---|---|
| Адресное хранение (ячейки) | **Есть** | `StockBin`, приёмка сканером `lib/warehouse/scan-receive.ts` |
| Приёмка, движения, остатки | **Есть** | append-only журнал движений, отчёты, сторно |
| Себестоимость с доставкой и таможней | **Есть** (с 01.09) | PR #123, разнесение ввоза по строкам |
| Массовая загрузка **товаров** из файла | **Нет** | `app/api/parts/import` заводит только справочник `PartReference`, без цен и остатков |
| Выгрузка на Avito / Drom / Авто.ру | **Нет** | XML-роутов нет вовсе |
| Онлайн-оплата картой | **Нет** | ни модели платежа, ни эквайринга |
| Кассовые чеки (54-ФЗ) | **Нет** | фискализации нет |
| Возвраты | **Нет** | модели возврата нет; `PartOrderStatus` = PROCESSING/SHIPPED/COMPLETED/CANCELLED |
| Отправка клиенту ссылок в SMS/Telegram | **Нет** | SMS уходит только с паролем и кодом восстановления (3 места) |
| Проценка по прайсам поставщиков | **Нет** | прайс-листов поставщика нет, есть только заказы |
| Мобильное приложение | **Нет** | и манифеста PWA тоже нет |
| API для мобильного клиента | **Нет** | 164 серверных действия, 26 роутов — почти все внутренние |

## Решения

**1. Мобильных приложений будет два (решение владельца, 01.09).** Клиентское — заказы,
запись на сервис, кабинет. Админское — сервис, магазин и аренда в руках у сотрудника. Это
намеренно разные продукты: у них разные пользователи, разные права и разный ритм выпуска,
и попытка сложить их в одно приложение кончается экраном, где половина кнопок скрыта по роли.

Прежняя редакция этого PRD объявляла приложение ненужным. Это было превышением полномочий:
аргументы (два стора, цикл релизов, трафик из браузера) остаются в силе как цена, но решение
о том, платить ли эту цену, принимает владелец, а не автор документа.

Ключевое следствие, которое эта редакция обязана назвать вслух: **у нас нет API**. Сто
шестьдесят четыре серверных действия и двадцать шесть роутов, из которых почти все —
внутренние. Серверные действия из мобильного приложения не вызываются. Поэтому первой идёт не
аппа, а API-слой и токенная авторизация — общий фундамент для обоих приложений.

**Сначала iOS, Android потом** (решение владельца, 01.09). Именно поэтому приложения пишутся
на кроссплатформенной основе, а не нативно под iOS: Android не «когда-нибудь переделаем», а
вторая сборка из той же кодовой базы, когда владелец скажет. Нативная разработка под iOS дала
бы чуть лучший результат сейчас ценой второго написания приложения потом.

**Приложение — платформенное, а не «приложение Гелеотеки».** Одна кодовая база, один листинг
в сторе, сервис определяется учётной записью и подставляет своё название, логотип, цвета и
контакты из настроек тенанта. Отдельная сборка под каждого клиента (white-label) — платная
опция на будущее, и у неё есть неочевидное ограничение: Apple требует, чтобы приложения,
собранные по шаблону для клиента, публиковались **с аккаунта разработчика самого клиента**
(Guideline 4.2.6). То есть white-label — это не только сборка, но и работа с чужим аккаунтом,
и это надо закладывать в цену подписки, а не в разработку.

**2. Проценка переосмыслена.** У Bazon проценка — поиск детали по прайсам российских
поставщиков в один клик. Дословный перенос нам бесполезен: мы не закупаем в РФ. Полезна её
изнанка — **расчёт цены под заказ**: взять цену поставщика, добавить доставку по весу, таможню
и наценку, и получить сумму, которую можно назвать клиенту, не считая в уме. Механика ввоза
уже написана (`lib/suppliers/landed-cost.ts`), не хватает экрана и прайса поставщика.

**3. Оплата, чеки и возвраты — одна история, а не три.** Принять деньги онлайн, не выдав чек,
нельзя по 54-ФЗ. Продавать дистанционно без возврата нельзя по ЗоЗПП. Значит, либо всё три,
либо ничего: половина — это работающая касса без чека, то есть нарушение.

**4. Первым идёт наполнение, а не витрина.** Выгрузка на Avito при пустом каталоге выгружает
пустоту. Порядок: прайс из файла → площадки → всё остальное.

## Пользователи

- **Менеджер** — заводит товары, называет цену, отправляет клиенту ссылку, оформляет возврат.
- **Клиент** — находит деталь (в поиске или на Avito), платит картой, получает чек и статус.
- **Владелец** — видит, откуда пришли продажи и сколько на них заработано.

## Объём

### Story A. Прайс из файла: массовое заведение товаров

**Проблема.** Каталог наполняется руками по одной позиции. У поставщика прайс на сотни строк.
Импорт, который уже есть, заводит только номенклатуру — имя и OEM — без цены, остатка,
состояния и склада. Продавать по нему нельзя.

**Что делаем.** Импорт товаров: вставка таблицы или загрузка CSV/XLSX со столбцами
OEM, название, цена, количество, склад, состояние, заметка, происхождение. Предпросмотр
до записи: сколько строк создастся, сколько обновится, какие отклонены и почему. Повторная
загрузка того же файла обновляет цены и остатки, а не плодит дубли.

**Для платформы.** Склад по умолчанию, состояния и разделители берутся из настроек тенанта:
у другого сервиса и склад другой, и прайс приходит в своём формате.

**Границы.** Загрузка фотографий пачкой — нет: у б/у деталей фотографии свои, их привязка по
файлу — отдельная работа.

### Story B. Выгрузка на Avito и Drom

**Проблема.** Живой спрос на детали к G-Class — на Avito, а не в поиске. Наш SEO растёт
медленно; статьи и модельные страницы работают на узнаваемость, а не на сделку.

**Что делаем.** XML-фид по официальной схеме автозагрузки Avito, отдельным адресом, с полями
категории «Запчасти и аксессуары»: OEM, марка, состояние (новое/б/у), цена, фотографии,
описание, адрес. Только активные позиции с положительным остатком. Продали — из фида ушло.
Второй фид — Drom, по их схеме.

**Границы.** Приём заказов с площадки внутрь CRM — нет: у Avito это отдельный API и отдельные
права. Первый шаг — попасть в выдачу площадки, а разговор ведём в мессенджере, как сейчас.

**Для платформы.** Адрес, контакты, категория и учётная запись площадки — настройки тенанта.
Адрес фида уже сейчас читается из CMS, и это ровно то, что делает фид переносимым: у второго
сервиса он заработает без правки кода. Тариф площадки каждый сервис оплачивает сам.

**Требует решения владельца.** Автозагрузка на Avito — платный тариф для профессиональных
продавцов. Без него фид не подключить. Точную цену смотреть на момент подключения; бюджет
подтверждает владелец.

### Story C. Ссылка клиенту в SMS и Telegram

**Проблема.** SMS уходит только с паролем. Смету, счёт и статус заказа клиент видит, если сам
зайдёт в кабинет. Менеджер пересылает ссылки руками из своего телефона.

**Что делаем.** Отправка клиенту ссылки одной кнопкой: смета на согласование, статус заказа,
готовность машины. SMS уже подключена, Telegram-прокси для сотрудников работает; клиенту в
Telegram — только если он сам написал боту (иначе Bot API не даст).

**Для платформы.** Имя отправителя SMS, бот Telegram и домен ссылок — у каждого сервиса свои.
Сейчас отправка привязана к одному набору ключей; спецификация выносит их в настройки тенанта.

**Границы.** Не автоматические рассылки. Отправляет менеджер, руками, по конкретному поводу:
согласие на рекламные сообщения мы не собирали, а 38-ФЗ за это штрафует.

### Story D. Проценка в нашей форме: цена под заказ

**Проблема.** Цену детали под заказ считают в уме или в таблице: цена поставщика, вес,
доставка, таможня, наценка. Ошибка в любом множителе — продажа в минус.

**Для платформы.** Ставки ввоза, валюта и наценка — параметры тенанта и поставщика. Сервис,
закупающий в РФ, просто оставит ставки ввоза пустыми и получит калькулятор наценки.

**Что делаем.** Прайс поставщика (тот же импорт, что в Story A) и экран расчёта: выбрал
позицию — увидел закупку, ввоз по нашим ставкам, себестоимость, цену при заданной наценке.
Кнопка «завести товар» переносит расчёт в каталог.

### Story E. Оплата картой, чеки и возвраты

**Проблема.** Заказ оформляется, деньги берутся вне системы. Для трафика с площадок это тупик:
человек, пришедший с Avito, не поедет в офис платить.

**Что делаем.**
- Эквайринг (ЮKassa либо банк владельца) со статусами платежа и вебхуком подтверждения.
- Фискальный чек через ОФД провайдера эквайринга: чек на приход при оплате, чек на возврат при
  возврате. Без чека платёж не считается принятым.
- Возврат: заявка клиента, решение менеджера, возврат денег и **возврат детали на склад**
  движением, а не правкой остатка. Для б/у экземпляра — обратно в продажу той же строкой.

**Для платформы.** Ключи эквайринга, касса, ОФД и реквизиты — у каждого сервиса свои, и это
не настройка «на будущее»: чужие платёжные ключи в общем коде недопустимы в принципе. Здесь
мультиарендность перестаёт быть архитектурной опрятностью и становится требованием.

**Требует решения владельца** (без этого история не стартует):
- юридическое лицо и система налогообложения — от них зависит ставка НДС в чеке;
- эквайер и ОФД;
- касса: облачная аренда или своя.

**Границы.** Рассрочка, оплата частями, оплата при получении — нет.

### Story F. Клиентское приложение

**Что делаем.** iOS и Android: вход, запись на сервис, заказы запчастей и их статусы, смета на
согласование, гараж клиента, аренда, пуш-уведомления. Спецификация:
`docs/plans/2026-09-01-mobile-client-app.md`.

### Story G. Админское приложение

**Что делаем.** iOS и Android для сотрудников: заказ-наряды, склад со сканером камерой,
магазин, аренда, задачи CRM, пуши сотрудникам. Главный выигрыш против браузера — приёмка на
складе: камера, ячейки и работа при плохой связи. Спецификация:
`docs/plans/2026-09-01-mobile-admin-app.md`.

### Story H. Фундамент обоих приложений: API и токенная авторизация

**Что делаем.** Версионированный REST под `/api/mobile/v1`, поверх существующей доменной
логики, и авторизация по токену вместо cookie. Без этого F и G не начинаются. Спецификация:
`docs/plans/2026-09-01-mobile-api-foundation.md`.

**Аккаунт разработчика Apple есть, подписка активна** (владелец, 01.09) — выпуск перестал
быть блокирующим. Остаётся уточнить одну деталь, и она не про технику: аккаунт личный или на
юридическое лицо. От этого зависит имя продавца в карточке приложения и возможность в будущем
публиковать сборки для клиентов платформы — Apple требует, чтобы приложения, собранные по
шаблону, шли с аккаунта самого клиента (Guideline 4.2.6). На ближайшую работу это не влияет:
фундамент и оба приложения пишутся одинаково.

## Порядок

```
A (прайс из файла) ──▶ B (Avito/Drom) ──▶ E (оплата+чеки+возвраты)
       └──────────────▶ D (цена под заказ)
C (ссылки клиенту) — независима, делается когда угодно

H (API + токены) ──┬──▶ G (админское приложение)
                   └──▶ F (клиентское приложение)
```

A первая: она наполняет то, что показывают B и продают E. C ни от чего не зависит и стоит
меньше всего. E последняя: она упирается в решения владельца и в деньги.

Ветка приложений идёт своим ходом и начинается с H — API нужен обоим. Из двух приложений
раньше окупается **G**: складская работа руками с телефона даёт выигрыш сразу, а клиентское
приложение имеет смысл, когда в магазине есть товар (A) и его можно оплатить (E).

## Как поймём, что сработало

- **A** — каталог наполняется файлом за минуты; повторная загрузка не плодит дублей.
- **B** — объявления живут на площадке, в Метрике виден переход, в CRM — обращение с Avito.
- **C** — менеджер перестал пересылать ссылки из личного телефона.
- **D** — цена под заказ называется с экрана, а не из таблицы.
- **E** — заказ с площадки оплачивается онлайн, чек приходит клиенту, возврат проводится
  движением по складу.
- **H** — приложение получает данные и права по токену; попытка чужого тенанта отбита тестом.
- **G** — приёмка десяти позиций делается сканером с телефона; отключение сети посреди приёмки
  не теряет данные и не задваивает приход.
- **F** — клиент получает пуш о готовой смете и соглашается с неё же, не открывая браузер.

Отдельный критерий для всего документа: **вторая установка платформы** заводится настройками,
без правки кода. Пока это не так, продукта нет, есть сайт одного сервиса.

## Чего мы сознательно не берём

- Проценку по российским прайсам (решение 2) — заменена расчётом цены под заказ.
- Приложение как обёртку сайта в webview: Apple такие отклоняет (Guideline 4.2), и оно не даёт
  ни сканера, ни офлайна — то есть ровно того, ради чего приложение и делается.
- Приём заказов площадки внутрь CRM.
- Автоматические рекламные рассылки.
