## Зачем второй контур

Шов изоляции уже добавляет условие по арендатору в каждый запрос. Он защищает от
забывчивости, но не от обхода: код может взять клиент напрямую, а сырой SQL — вообще пройти
мимо. RLS закрывает именно это: политика живёт в базе и не зависит от того, каким путём пришёл
запрос.

## Что проверено на копии боевой схемы

Отдельная роль `app_runtime` (не владелец таблиц, без BYPASSRLS), политика
`USING ("tenantId" = current_setting('app.tenant_id', true))` на `Deal` и `User`:

| Проверка | Результат |
|---|---|
| Забытое условие, арендатор НЕ установлен | **0 строк** — политика закрывается, а не открывается |
| Арендатор установлен, запрос без условия | только свои строки |
| Явный запрос чужой сделки по идентификатору | пусто |
| Попытка записать строку чужому арендатору | **отказ базы**: new row violates row-level security policy |
| Владелец схемы (не runtime-роль) | видит всё — поэтому приложение обязано ходить НЕ владельцем |

Последняя строка — главное условие: пока приложение подключается владельцем таблиц, RLS
бесполезен. Значит веха невозможна без новой роли и смены строки подключения на проде.

## Развилка: как ставить арендатора

RLS читает `app.tenant_id` из настроек сессии. Пул соединений делает пожизненную установку
опасной: соединение с чужим арендатором вернётся в пул и достанется следующему запросу.
Отсюда два способа, и выбор между ними — решение владельца, потому что это про деньги и
скорость, а не про вкус.

### Способ А. Транзакция на запрос

Каждый запрос оборачивается в транзакцию, внутри которой `set_config('app.tenant_id', …, true)`
действует только до её конца.

**Замерено** (локальная база, 300 запросов на замер):

| | мс на запрос |
|---|---|
| обычный запрос | 0,20 |
| транзакция без установки | 0,43 |
| транзакция + `set_config` | 0,53 |

То есть **+0,34 мс** на запрос локально. В бою добавится сеть: транзакция — это лишние
обращения к базе (начало, установка, конец), и на странице с десятком запросов набежит
заметнее, чем выглядит по проценту. Отдельный расход — удержание соединения: интерактивная
транзакция занимает его целиком, и при небольшом пуле это ограничивает одновременность.

**Плюс:** работает с любым числом арендаторов, ничего не надо держать в памяти.

### Способ Б. Пул на арендатора

Соединения открываются с параметром `options=-c app.tenant_id=…`, и установка происходит один
раз при соединении.

**Плюс:** ноль накладных расходов на запрос.
**Минус:** пул на каждого арендатора. Для десятка сервисов — нормально, для сотни — надо
закрывать простаивающие, и это отдельный механизм.

### Рекомендация

**Способ А** на старте: он не требует нового механизма и не зависит от числа арендаторов, а
0,34 мс на запрос — цена, которую видно только в нагрузочном тесте. Способ Б имеет смысл, если
измерения на проде покажут, что транзакции упираются в размер пула.

## Порядок работ, когда способ выбран

1. Роль `app_runtime` на прод-базе, права на схему, **без** BYPASSRLS и не владелец.
2. Политики на всех таблицах с колонкой арендатора — генерируются из классификации, как и
   прошлые миграции.
3. Приложение переводится на новую строку подключения. **Это единственный шаг с простоем в
   случае ошибки**, поэтому он делается при владельце и с готовым откатом: вернуть прежний
   `DATABASE_URL` одним изменением конфига.
4. Шов начинает устанавливать арендатора выбранным способом.
5. Негативный тест на живой базе: под runtime-ролью забытое условие отдаёт ноль строк.

## Чего делать нельзя

- Включать RLS, пока приложение ходит владельцем таблиц: политика будет висеть, ничего не
  защищая, и создаст ложное ощущение сделанного.
- Ставить `app.tenant_id` без `true` (без ограничения транзакцией): значение переживёт возврат
  соединения в пул и достанется чужому запросу. Это худший из возможных исходов — не отказ, а
  тихая выдача чужих данных.
