## 0. Схема работы В ЭТОЙ ЗАДАЧЕ — ОБРАТНАЯ обычной

Владелец сказал дословно: **«Делай сам, codex — adversarial review.»**

То есть: **код пишет Claude**, codex только ищет дефекты и НЕ правит. Это
отличается от прежней схемы (планы и код от codex), и отличие намеренное —
предыдущий подход дал «баг на баге», владелец потребовал полноценное решение.

Вызов codex (бинарь `omc` НЕ в PATH):

```
node ~/.claude/plugins/cache/omc/oh-my-claudecode/4.15.7/bin/oh-my-claudecode.js ask codex --prompt "..."
```

Codex не делает git-операций. Ответ падает в `.omc/artifacts/ask/*.md`
(путь — последняя строка stdout). Ждать ОДНИМ фоновым ожидателем на задачу:
`while pgrep -f "ask codex" >/dev/null; do sleep 60; done` — паттерн ловит
ЛЮБОЙ процесс codex, поэтому несколько ожидателей плодят дубликаты.

**Заявления codex проверять своим контрольным прогоном.** Он уже выдумывал
факты («production SELECT»), которых в коде не было.

### НЕОТВЕЧЕННЫЙ вопрос владельца — ответить в первом же сообщении

> «Нам вообще нужен бот? Почему мы не можем отправлять эти сообщения напрямую
> с платформы телеграм-аккаунту?»

Готовый ответ по итогам ресерча: **нужен, альтернативы нет.** Telegram не даёт
способа написать произвольному аккаунту «с платформы». Есть ровно два пути:
(а) Bot API — получатель сам начинает диалог с ботом, это наш случай;
(б) MTProto от имени живого пользовательского аккаунта — это работа под чужой
учёткой, против духа условий, аккаунт улетает в бан, для рабочего процесса
сервиса непригодно. Что НЕ обязательно — так это webhook-приём: от него мы как
раз ушли. Бот при этом остаётся.

## 2. Корень проблемы (установлен, не гипотеза)

Аудит записывал `Сбой ответа Telegram-бота`, код `TELEGRAM_NETWORK`,
`HTTP: нет ответа` — то есть от `api.telegram.org` не приходило ВООБЩЕ ничего.
Экран операций: медиана 5.1 с, максимум 10 с, одна отправка «Отказ · медленно
10 с», одна «Успех 253 мс». При этом наш endpoint отвечает снаружи за 0.21 с,
а другой HTTPS-исход (Resend) работает штатно.

Вывод: деградирован именно путь Timeweb↔Telegram. Совпадает с подтверждённым
замедлением Telegram со стороны РКН (февраль 2026, заявлены планы полной
блокировки). Отсюда две меры: уход с webhook на опрос и настраиваемый релей.

Опровергнутые по дороге гипотезы (не возвращаться): битый/обрезанный токен
привязки (токен был ровно 43 валидных символа, регексп совпадал), антиспам
Telegram, сломанный `after()`.

## 3. Ресерч — выжимка

- `getUpdates` и webhook взаимоисключающи: при активной регистрации опрос
  отдаёт 409 «can't use getUpdates method while webhook is active».
- 409 приходит ТАКЖЕ при двух параллельных `getUpdates` («terminated by other
  long poll») — это критично для находки №1 ниже.
- `deleteWebhook` принимает `drop_pending_updates`.
- Длинный опрос — `timeout` 30–60 с; мы намеренно используем короткий
  (`timeout: 0`), потому что drain живёт внутри HTTP-запроса.
- `sender_chat` — отправитель, когда пишет анонимный администратор группы.
- Обходной путь сообщества при замедлении — HTTPS-прокси и настраиваемый базовый
  адрес Bot API.

## 5. Adversarial review codex — 10 находок, ЭТО И ЕСТЬ РАБОТА

Полный отчёт: `.omc/artifacts/ask/codex-adversarial-review-claude-telegram-*.md`

**№6 ПОДТВЕРЖДЁН МНОЙ фактической проверкой БД.** Миграция
`20260802190000_telegram_test_notification` пересоздаёт CHECK
`TelegramSendAttempt_operation_check` без `UPDATES_POLL`; в базе сейчас только
три старые операции. Значит диагностика опроса не пишется вообще (исключение
глотается в `recordTelegramSendDiagnostic`), экран операций по polling пуст.
Чинить новой миграцией с полным списком из четырёх операций.

Остальные девять — **со слов codex, каждую проверять своим прогоном**:

| № | Severity | Суть |
|---|----------|------|
| 1 | BLOCKER | 409 бывает и от параллельного getUpdates, а я на любой 409 зову `deleteWebhook` — снесу чужую регистрацию и замаскирую собственный overlap. Нужен single-flight lease + `getWebhookInfo` вместо слепого удаления. |
| 2 | BLOCKER | Нет защиты от ядовитого апдейта: при стабильном исключении виновник навсегда первый в очереди, всё за ним встаёт. Нужен durable счётчик попыток + карантин. Правдоподобный триггер — коллизия `@@unique([tenantKey, chatId])` при миграции группы. |
| 5 | BLOCKER | Рецепт Cloudflare Worker в runbook логирует токен: observability включена по умолчанию, invocation log пишет полный URL, а токен лежит в пути. Моя фраза «Worker не хранит и не логирует токен» — ложная, чинить рецепт или убирать. |
| 3 | MAJOR | `budgetMs` не wall-clock: проверяется только перед батчем; реальный drain доживает до ~16 с при заявленных 3. Может срубить весь maintenance-тик. |
| 4 | MAJOR | Провал опроса возвращает 200 `{ok:true}` — cron зелёный при мёртвом канале. Нужен health-contract. |
| 10 | MAJOR | Тест «stale drain» ничего не доказывает: два drain не запускаются, fake не моделирует Prisma. Нет тестов на poison, дедлайн, провал deleteWebhook, оба вида 409, backlog. Обвязка `updates-runtime` не покрыта вовсе. |
| 7 | MINOR | Ответы бота в polling-обвязке фактически не awaited: scheduler типизирован `void`, processor зовёт без `await`. |
| 8 | MINOR | После истечения ссылки watcher залипает в `expired`; новая ссылка сразу «истёкшая». Нужен `key` на компоненте. |
| 9 | MINOR | `TELEGRAM_API_BASE_URL` не `secret`, но runbook требует беречь как токен; `normalizeTelegramApiBaseUrl` не вызывается при сохранении — невалидное значение молча выключает канал. |

Порядок работы: №6 (подтверждён) → три BLOCKER → MAJOR → MINOR → контрольные
прогоны → PR. После правок — второй заход codex на adversarial review.

## 6. Ограничения проекта — нарушать нельзя

- **Пароль вводить нельзя.** Расширение Chrome не имеет доступа к geleoteka.ru,
  сессия истекла. Визуальную проверку прода просить у владельца.
- **Прод-БД снаружи недоступна** (анти-DDoS), `DATABASE_URL` в окружении =
  localhost. Логи прода — через `twc-api`.
- Миграции **пишутся руками** и применяются `prisma migrate deploy`
  (`migrate dev` требует reset из-за известного дрейфа).
- В `migration.sql` **НИКОГДА** не включать дрейф: `DROP INDEX
  "Part_photos_gin_idx"`, `DROP INDEX "Vehicle_photos_gin_idx"`, переименование
  индекса `StockMovement`. Доказательство соответствия схеме —
  `npx prisma migrate diff --from-schema-datamodel prisma/schema.prisma
  --to-schema-datasource prisma/schema.prisma --script`.
- Prisma-клиент импортируется из `@/app/generated/prisma/client`, НЕ из
  `@prisma/client`; типы теряются через синглтон `@/lib/db` — нужны явные
  утверждения типов.
- Next.js здесь **модифицированный форк**: перед кодом читать
  `node_modules/next/dist/docs/`. Middleware — `proxy.ts` в корне.
- `gh pr merge` виснет через прокси rtk. Мержить:
  `gh api -X PUT repos/0pt1m1sm/geleoteka/pulls/N/merge -f merge_method=squash`.
  Удаление веток и часть `gh` блокирует классификатор — просить владельца
  запустить через `!`.
- Ветки за собой чистить (владелец делал замечание).

### Политика содержимого Telegram-сообщений (владелец, многократно)

**Можно:** имя клиента, номер сделки.
**Нельзя:** тема, тело, телефон, адрес, email, госномер, VIN, имя файла
вложения, причина отказа и любые URL из письма или пользовательского ввода.
**Никогда не логировать:** `chat_id`, токен бота, URL Bot API, сырые апдейты.

## 8. Порядок работ — ЭТАП 1 ЭТО ПРОВЕРКА, НЕ ПРАВКИ

Владелец распорядился: **первым этапом полностью проверить план.** Ни одной
строки исправлений, пока все десять находок не получат собственный вердикт.
Причина прямая — из §5 моей проверкой подтверждена ровно ОДНА находка, а
остальные девять существуют только как утверждения codex, который в этом
проекте уже выдумывал факты.

### Этап 1 — верификация (сначала целиком, потом всё остальное)

0. Ответить на вопрос про бота (§1) — коротко, он ждёт ответа.
1. `git checkout claude/telegram-polling-architecture`, сверить `git log`
   (ожидается `bfe46ce`), убедиться что рабочее дерево чистое.
2. Прочитать отчёт codex целиком из `.omc/artifacts/ask/`.
3. По КАЖДОЙ из десяти находок вынести вердикт **ПОДТВЕРЖДЕНО / ОПРОВЕРГНУТО /
   ЧАСТИЧНО**, приложив конкретное доказательство, а не рассуждение:
   - дефект в коде → контрольный прогон: сломать защиту, увидеть падение,
     восстановить, увидеть зелено; либо тест, воспроизводящий дефект;
   - дефект в БД/миграции → фактический запрос к локальной базе;
   - дефект в поведении Telegram API → ссылка на документацию;
   - дефект в UI → проверка геометрии/состояния, а не «на глаз».
4. Свести вердикты в таблицу и **пересобрать план правок по подтверждённому**.
   Опровергнутое выкинуть и записать, почему — чтобы не всплыло снова.
   Ожидать, что часть находок не подтвердится: это нормальный исход ревью.
5. Показать владельцу пересобранный план до начала правок.

Полезно знать заранее: находка №6 уже подтверждена фактической проверкой
(в базе CHECK содержит три операции вместо четырёх), находки №1 и №5
опираются на внешнюю документацию и проверяются чтением первоисточника,
№8 и №9 — самые дешёвые для проверки, №10 про качество тестов проверяется
попыткой написать падающий тест на заявленную дыру.

### Этап 2 — правки

Чинить только подтверждённое, по возрастанию риска: №6 → BLOCKER → MAJOR →
MINOR. На каждую защиту — контрольный прогон (ломаем → тест обязан упасть →
чиним → зелено). Без контрольного прогона защита считается недоказанной.
