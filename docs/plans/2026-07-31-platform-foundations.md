## Целевая модель (для сверки решений; реализуется позже)

Четыре уровня: **Платформа → Тенант → Точка (филиал) → Клиент**. Тенант ≠ точка: сеть из пяти
автосервисов — это один тенант с пятью точками (общая клиентская база, общий персонал).

Вход и клиентская карточка разделены:

```
Account (глобальный) ── AuthIdentity (подтверждённые email/телефон/OAuth)
   └── Membership → Тенант → Party (человек ИЛИ организация) → TenantCustomer
                                        └── машины, сделки, заказ-наряды
```

Один человек может быть клиентом в двух тенантах: **вход один, карточки полностью изолированы**,
межтенантной дедупликации по email нет, тенант не видит чужие членства. Роли принадлежат связке
«человек ↔ тенант»: проверка звучит «админ в ЭТОМ тенанте и на ЭТОЙ точке». Вход поддержки —
только явная имперсонация: ограничение по времени, причина, запись в журнал, видимая пометка в UI.

### Story 1.5: Аудит каскадов и связей  ⚠️ GATED (целостность данных)

**Objective** (запрос владельца 2026-07-31): есть сущности, которые не могут жить без родителя.
Если удалить сделку, а заказ-наряд останется — это недоработка, оставляющая мусор в системе.
Нужна не выборочная, а **полная** проверка всех связей схемы.

**Проверить по каждой связи** (98 моделей), с учётом того, что дефолт Prisma различается:
для обязательной связи — `Restrict`, для необязательной — `SetNull`. То есть отсутствие явного
`onDelete` уже означает разное поведение, и именно там прячутся сюрпризы.

Классификация:
1. **Сирота** — потомок переживает удаление родителя, хотя без него бессмысленен. Живой риск
   только если родителя реально можно удалить из кода (проверять `.delete(`/`.deleteMany(`).
2. **Переудаление** — каскад уносит записи самостоятельной ценности (финансовые, юридические,
   аудиторские). Мы уже поймали такое на `Deal`/`RepairOrder → User`; искать то же в других местах.
3. **Корректно** — каскад внутри агрегата, где «удалить родителя» действительно значит «удалить части».
4. **Заблокировано** — `Restrict` там, где законное удаление становится невозможным и оператор
   упирается в тупик без пути в интерфейсе.

**Особое внимание:** `Deal → RepairOrder/Estimate`, `RepairOrder → JobLine/Slot/RepairOrderPhoto`,
`Vehicle → RepairOrder/RentalBooking`, резервирования запчастей, склад,
`LoyaltyAccount → LoyaltyTransaction`, почтовые таблицы, и новые таблицы от 30–31 июля
(`WorkingHours`, `ScheduleException`, `BlockedInterval`, `TeamMember`).

**DoD:**
- [ ] Составлена таблица «родитель → потомок, текущее правило, класс, последствие, рекомендация».
- [ ] Каждая найденная сирота либо исправлена, либо осознанно оставлена с обоснованием в плане.
- [ ] Для исправленных — тест или проверка на живых данных (транзакция с откатом), что удаление
      родителя больше не оставляет мусор и не уносит лишнего.
- [ ] Миграции без постороннего дрейфа Prisma (см. конвенцию выше).

### Story 2: Ресурсная модель расписания  ⚠️ GATED (схема + бронирование)

**Objective:** `Slot.dateTime` уникален **глобально** — это модель «один пост на всю систему».
Автосервис с двумя подъёмниками уже сегодня не может работать. В схеме это отмечено как временное
упрощение (`prisma/schema.prisma`, комментарий над `model Slot`).

**Design:**
- Новая сущность `ServiceResource` (пост / бригада / подъёмник): `id`, **`tenantId`**, `name`,
  `isActive`, `sortOrder`. Ёмкость автосервиса — три слоя (механики, посты, оборудование);
  закладываем ресурс как расширяемую сущность, но сложную capacity-модель НЕ строим.
- Бронь резервирует пару «ресурс + интервал»: `Slot` получает `resourceId`, `startAt`, `endAt`.
- **Защита от пересечений — `EXCLUDE USING gist`** по `(resourceId WITH =, tstzrange(startAt, endAt) WITH &&)`.
  Уникальность по моменту начала (как сейчас) **не ловит наложение по длительности** — это главная
  причина менять механизм, а не только добавлять ресурс.
  Требуется расширение `btree_gist`.
- Миграция: завести ресурс по умолчанию, привязать к нему существующие брони, вычислить `endAt`
  из `SLOT_MINUTES`. Существующие записи не теряются.

**Не сломать:**
- `lib/scheduling/availability.ts` — чистый движок, покрыт 24 тестами.
- Контракт `/api/slots` → `{ time, available }[]`: время доступно, если **свободен хотя бы один
  ресурс**. Контракт сохраняется, меняется только вычисление.
- Освобождение слота при отмене (`app/actions/admin.ts`), перенос записи (`lib/scheduling/reschedule.ts`).

**DoD:**
- [ ] Два поста → две записи на одно время проходят; третья отвергается.
- [ ] Пересечение по длительности отвергается (старый механизм этого не умел) — тест.
- [ ] Существующие брони после миграции целы и привязаны к ресурсу по умолчанию.
- [ ] `/api/slots` отдаёт прежний контракт; клиентская запись работает.
- [ ] Verify: тесты движка + E2E против живой БД + `npm run build` + `npm run lint`.

### Story 3: Приватные фото работ  ⚠️ GATED (доступ к персональным данным)

**Objective:** фото машин клиентов (`RepairOrderPhoto`) грузятся через `/api/upload` и отдаются
`/api/images/<id>` **без какой-либо авторизации**, с заголовком `public, max-age=31536000, immutable`.
Защита — только неугадываемость cuid, то есть «секретная ссылка»: её нельзя отозвать, она оседает
в истории браузера, в реферере и в кэше прокси. На снимках бывают номера, VIN, повреждения, салон.

**Сложность:** по тому же маршруту идут **публичные** фото каталога запчастей и аренды, которые
обязаны открываться всем. Просто добавить проверку нельзя.

**Design:** разделить публичные и приватные изображения (флаг на `UploadedImage` либо отдельный
маршрут). Приватные: только сотрудник (ADMIN/MANAGER/MASTER) или владелец машины; `Cache-Control:
private, no-store`; отдавать `Content-Disposition` без inline-исполнения.

**DoD:**
- [ ] Фото работ недоступно анонимно (401/403) и доступно сотруднику и владельцу.
- [ ] Публичный каталог запчастей и аренды продолжает открываться анонимно.
- [ ] Приватные снимки не кэшируются как публичные.
- [ ] Verify: тесты авторизации маршрута + проверка заголовков.

### Story 5: Подтверждение email  ⚠️ GATED (аутентификация)

### Story 7: Создание из контекста — сделка из карточки клиента, заказ-наряд вручную

**Objective:** дать менеджеру завести заказ-наряд прямо на `/admin/repair-orders`.

**Проблема.** Заказ-наряд рождается только двумя путями: онлайн-бронирование
(`app/actions/booking.ts`) и согласование сметы по сделке, где его создаёт
`dispatchFulfillment` (`app/actions/crm/estimates.ts:321`,
`app/actions/customer-estimates.ts:106`). Ручного создания нет — страница только
показывает, меняет статус и удаляет. Клиент «приехал без записи» вынуждает
менеджера завести сделку, выдумать смету и согласовать её, чтобы получить наряд.

**Ограничение, которое нельзя нарушить.** `RepairOrder.dealId` обязателен и
каскадит от сделки: наряд не может существовать без сделки. Значит форма либо
привязывает к существующей сделке клиента, либо создаёт сделку и наряд в одной
транзакции — как это уже делает `createDealManually` для сделок.

**Files:** `app/actions/repair-orders.ts` (новое действие), форма-диалог,
`app/(admin)/admin/repair-orders/page.tsx` (кнопка).

**Второй случай той же природы.** `NewDealDialog` смонтирован только на
`/admin/crm/deals` и принимает полный список клиентов — режима «клиент уже
известен» у него нет. Из карточки клиента сделку не завести: вкладка «Сделки»
только перечисляет, а в пустом состоянии пишет «У клиента ещё нет сделок» и не
предлагает её создать. Менеджер уходит в раздел сделок и там ищет клиента,
которого только что смотрел.

Общий дефект: создание живёт только в разделе-списке, а не там, где менеджер уже
находится и где контекст известен.

**DoD:** менеджер создаёт наряд с выбором клиента, машины (необязательной — поле
теперь nullable) и сделки; при отсутствии сделки она создаётся тут же; номер
выдаётся `nextRepairOrderNumber`. `NewDealDialog` принимает предвыбранного
клиента и выводится на вкладке «Сделки» в карточке, включая пустое состояние.
Проверено на живых данных с откатом.

### Story 1.5 — аудит выполнен 2026-07-31, найдено 9 проблем

Аудит 77 связей в 61 модели. Ключевое (проверено лично, не со слов агента):

1. **Утечка складских резервов.** Резерв под сметную строку связан НЕ внешним ключом, а строкой
   `<lineId>:reserve`, поэтому каскад БД его не вычищает. `deleteEstimateLine` снимает резерв
   вручную (правильный образец), а `deleteEstimate` и `deleteDeal` — нет. Зарезервированный остаток
   завышается необратимо, доступное количество падает без объясняющей записи.
2. **Комментарий у `deleteDeal` (`app/actions/crm/deals.ts:174-177`) утверждает
   `onDelete: SetNull` и «история работ выживает», тогда как в схеме `Cascade`.** Удаление сделки
   уничтожает заказ-наряд, работы, слот, фото и сметы. Единственная защита — запрет для выигранных.
3. `Vehicle → RepairOrder` и `Vehicle → RentalBooking` — `Cascade`: удаление машины сносит историю
   обслуживания и договор аренды. Тот же класс, что мы починили для `User` миграцией `20260730180000`.
4. `Part → PartOrderItem` и `Part → StockItem → StockMovement` — `Cascade` в аудиторский журнал
   движений; сегодня защищает один `if` в `lib/suppliers/order-lifecycle.ts`.
5. Удаление модели/поколения авто — без проверок, уносит комплектации и таблицу совместимости.
6. Задачи по удалённой сделке остаются `OPEN` навсегда (`Deal → CrmTask`, SetNull).
7. Входящее письмо при удалении записи общения остаётся `ASSIGNED` с мёртвой ссылкой — пропадает
   и из очереди разбора, и из карточки клиента.
8. Утечка байтов изображений: счётчик ссылок в `lib/uploads.ts` не знает про `RepairOrderPhoto`.
9. `SupplierOrder.userId` — единственный необработанный `Restrict`: пользователь-поставщик проходит
   все проверки стирания и падает с `P2003` уже после выгрузки и подтверждения.

**Таблицы, заведённые 30–31 июля** (`WorkingHours`, `ScheduleException`, `BlockedInterval`,
`TeamMember`) — **внешних ключей не имеют вообще**, осиротеть нечему. Отвязка команды от
пользователей оказалась единственным местом, где удаление безвредно по построению.
