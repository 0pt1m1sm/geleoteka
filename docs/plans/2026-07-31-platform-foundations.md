составные. Долг не должен расти.

## Целевая модель (для сверки решений; реализуется позже)

Четыре уровня: **Платформа → Тенант → Точка (филиал) → Клиент**. Тенант ≠ точка: сеть из пяти
автосервисов — это один тенант с пятью точками (общая клиентская база, общий персонал).

Вход и клиентская карточка разделены:

```
Account (глобальный) ── AuthIdentity (подтверждённые email/телефон/OAuth)
   └── Membership → Тенант → Party (человек ИЛИ организация) → TenantCustomer
                                        └── машины, сделки, заказ-наряды
```

Один человек может быть клиентом в двух тенантах: **вход один, карточки полностью изолированы**,
межтенантной дедупликации по email нет, тенант не видит чужие членства. Роли принадлежат связке
«человек ↔ тенант»: проверка звучит «админ в ЭТОМ тенанте и на ЭТОЙ точке». Вход поддержки —
только явная имперсонация: ограничение по времени, причина, запись в журнал, видимая пометка в UI.

### Story 2: Ресурсная модель расписания  ⚠️ GATED (схема + бронирование)

**Objective:** `Slot.dateTime` уникален **глобально** — это модель «один пост на всю систему».
Автосервис с двумя подъёмниками уже сегодня не может работать. В схеме это отмечено как временное
упрощение (`prisma/schema.prisma`, комментарий над `model Slot`).

**Design:**
- Новая сущность `ServiceResource` (пост / бригада / подъёмник): `id`, **`tenantId`**, `name`,
  `isActive`, `sortOrder`. Ёмкость автосервиса — три слоя (механики, посты, оборудование);
  закладываем ресурс как расширяемую сущность, но сложную capacity-модель НЕ строим.
- Бронь резервирует пару «ресурс + интервал»: `Slot` получает `resourceId`, `startAt`, `endAt`.
- **Защита от пересечений — `EXCLUDE USING gist`** по `(resourceId WITH =, tstzrange(startAt, endAt) WITH &&)`.
  Уникальность по моменту начала (как сейчас) **не ловит наложение по длительности** — это главная
  причина менять механизм, а не только добавлять ресурс.
  Требуется расширение `btree_gist`.
- Миграция: завести ресурс по умолчанию, привязать к нему существующие брони, вычислить `endAt`
  из `SLOT_MINUTES`. Существующие записи не теряются.

**Не сломать:**
- `lib/scheduling/availability.ts` — чистый движок, покрыт 24 тестами.
- Контракт `/api/slots` → `{ time, available }[]`: время доступно, если **свободен хотя бы один
  ресурс**. Контракт сохраняется, меняется только вычисление.
- Освобождение слота при отмене (`app/actions/admin.ts`), перенос записи (`lib/scheduling/reschedule.ts`).

**DoD:**
- [ ] Два поста → две записи на одно время проходят; третья отвергается.
- [ ] Пересечение по длительности отвергается (старый механизм этого не умел) — тест.
- [ ] Существующие брони после миграции целы и привязаны к ресурсу по умолчанию.
- [ ] `/api/slots` отдаёт прежний контракт; клиентская запись работает.
- [ ] Verify: тесты движка + E2E против живой БД + `npm run build` + `npm run lint`.

### Story 3: Приватные фото работ  ⚠️ GATED (доступ к персональным данным)

**Objective:** фото машин клиентов (`RepairOrderPhoto`) грузятся через `/api/upload` и отдаются
`/api/images/<id>` **без какой-либо авторизации**, с заголовком `public, max-age=31536000, immutable`.
Защита — только неугадываемость cuid, то есть «секретная ссылка»: её нельзя отозвать, она оседает
в истории браузера, в реферере и в кэше прокси. На снимках бывают номера, VIN, повреждения, салон.

**Сложность:** по тому же маршруту идут **публичные** фото каталога запчастей и аренды, которые
обязаны открываться всем. Просто добавить проверку нельзя.

**Design:** разделить публичные и приватные изображения (флаг на `UploadedImage` либо отдельный
маршрут). Приватные: только сотрудник (ADMIN/MANAGER/MASTER) или владелец машины; `Cache-Control:
private, no-store`; отдавать `Content-Disposition` без inline-исполнения.

**DoD:**
- [ ] Фото работ недоступно анонимно (401/403) и доступно сотруднику и владельцу.
- [ ] Публичный каталог запчастей и аренды продолжает открываться анонимно.
- [ ] Приватные снимки не кэшируются как публичные.
- [ ] Verify: тесты авторизации маршрута + проверка заголовков.

### Story 4: Журнал действий администратора  ⚠️ GATED (аудит)

**Objective:** журнала нет вообще — восстановить, кто и когда стёр клиента, сменил роль или вошёл
под другим пользователем, нечем. Нужен и сегодня (мы уже выкатили необратимое стирание ПД),
и обязателен для enterprise-продажи.

**Design:** `AuditLog` с **`tenantId`** (сразу, по правилу периода), `actorId`, `action`,
`targetType`, `targetId`, `metadata Json`, `ip`, `createdAt`. Запись — из server actions,
вне транзакции бизнес-операции (сбой журнала не должен откатывать саму операцию), но с гарантией,
что успешная операция всегда журналируется.

**Покрыть минимум:** стирание ПД клиента, архивирование/восстановление клиента, смена роли,
сброс пароля, блокировка/разблокировка, удаление пользователя, удаление члена команды.

**DoD:**
- [ ] Каждое из перечисленных действий оставляет запись с актором и целью.
- [ ] Журнал доступен только ADMIN; записи неизменяемы (нет UI правки/удаления).
- [ ] Сбой записи в журнал не откатывает бизнес-операцию, но логируется.
- [ ] Verify: тесты на запись журнала для каждого действия.

### Story 5: Подтверждение email  ⚠️ GATED (аутентификация)

**Objective:** подтверждения адреса нет вообще (`emailVerified`/`verificationToken` в схеме
отсутствуют), при этом email — основной идентификатор входа. Это уже приводило к дыре: автопривязка
OAuth по совпадению email давала админскую сессию без пароля (закрыто ограничением ролью `CLIENT`).

**Design:** подтверждение адреса при регистрации и при смене email. Учесть, что в целевой модели
это свойство `AuthIdentity` — значит хранить флаг и время подтверждения так, чтобы перенос был
механическим. Токены — одноразовые, с TTL, хранить хеш, а не сам токен.

**DoD:**
- [ ] Новый адрес не считается подтверждённым до перехода по ссылке.
- [ ] Повторная отправка ограничена по частоте; токен одноразовый и истекает.
- [ ] Решено и задокументировано, что делать с уже существующими неподтверждёнными адресами
      (не выкидывать действующих клиентов из системы).
- [ ] Verify: тесты флоу + проверка, что вход не сломан для текущих пользователей.

### Story 6: `requirePermission` как фасад авторизации  ⚠️ GATED (авторизация)

**Objective:** 186 вызовов `requireRole` в 72 файлах, разрешений нет, проверки владения ресурсом
делаются вручную в каждом месте. Цель — **остановить рост долга**, не переписывая всё сейчас.

**Design:** каталог разрешений (`estimate:approve`, `customer:erase`, …) и централизованный фасад
так, чтобы: (а) существующие `requireRole` продолжали работать; (б) новые фичи писались только
через фасад; (в) позже можно было заменить движок (роли → разрешения → отношения) **не трогая места
вызова**. Внешний движок (OpenFGA/Cedar) сейчас НЕ вводим — он оправдан после выхода за роли.

**DoD:**
- [ ] Фасад покрывает роли текущего enum и проверку владения ресурсом одной функцией.
- [ ] Хотя бы один существующий модуль переведён на фасад как образец.
- [ ] Задокументировано правило: новые фичи — только через `requirePermission`.
- [ ] Verify: тесты фасада + отсутствие регрессии в переведённом модуле.
