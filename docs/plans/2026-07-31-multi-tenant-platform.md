# Мультитенантная платформа: целевая модель и путь к ней

Created: 2026-07-31
Status: ПРИНЯТ 01.09.2026 — полный объём, параллельно с фундаментом мобильного API
Type: Architecture
Основано на: консультация codex (артефакт `.omc/artifacts/ask/codex-saas-crm-enterprise-*.md`),
собственное исследование практик (HubSpot, Salesforce, WorkOS, OpenFGA, Postgres RLS),
проверка текущей схемы.

## Решение владельца

Строим SaaS: автосервисы не хостят у себя. Схема должна быть универсальной и переносимой,
уровень — enterprise, а не pet project. Полная переделка допустима, если текущее сделано неверно.

## Короткий вердикт

Текущая модель **не готова** к мультитенанту и не «дорабатывается по краям»: `User` совмещает
пять ролей (личность, вход, клиент, сотрудник, поставщик), права лежат в JWT одним enum-полем,
десятки уникальностей глобальны, расписание предполагает один пост на всю систему.

Целевая архитектура:

- одна общая схема в PostgreSQL на региональную ячейку, `tenantId` во всех доменных таблицах;
- **RLS как обязательный второй контур** — «забытый `WHERE` не должен становиться инцидентом»;
- глобальный `Account` (вход) отдельно от `TenantMembership` (доступ к сервису) и `Party` (субъект CRM);
- кастомные роли + фиксированный каталог разрешений + несколько областей видимости данных;
- один централизованный слой политик, без внешнего движка авторизации на этом этапе;
- нумерация через счётчики тенанта, расписание через конкретные ресурсы и exclusion constraint.

**Оценка: 144–210 инженерных дней.** Командой из трёх инженеров с QA — 14–18 календарных недель.
Это не оценка «переписать за неделю»; объём соответствует уровню, который заказан.

## Почему нельзя обойтись малой кровью — цифры по репозиторию

| Что | Масштаб |
|---|---|
| `requireRole` | 186 вызовов в 72 файлах |
| `customerUserId` | 366 упоминаний в 66 файлах |
| Прямые обращения к Prisma | ~1000 мест в 214 файлах |
| Моделей в схеме | 98 |

## Критично: RLS без составных ключей не защищает

PostgreSQL проверяет ссылочную целостность **в обход RLS**. Значит политика изоляции сама по себе
не помешает создать ссылку на строку чужого тенанта — нужны составные внешние ключи
`(tenantId, id)`. Это не деталь реализации, а условие, без которого весь контур бессмысленен.

## Что уже есть в проекте (не с нуля)

Складской модуль **уже спроектирован под мультитенант**: составные ключи с `tenantKey`, ядро в
`lib/wms` не знает о хосте, связь через удаляемый адаптер `lib/wms-host` с комментарием «при
выделении WMS в отдельный продукт этот модуль заменяется». Значение пока захардкожено
(`TENANT_KEY = "geleoteka"`). Это рабочий шаблон — распространяем его, а не изобретаем второй подход.

| Что | Стоимость, дней |

| `permissionRole` в JWT → серверная валидация, версия роли | 15–22 |

## Что можно отложить без будущей переделки

Внешний движок авторизации (OpenFGA/Cedar), БД на тенанта, вторая региональная ячейка,
корпоративный SSO/SCIM, ключи шифрования клиента, произвольный ABAC, event sourcing,
партиционирование, межтенантная дедупликация.

## Чего откладывать НЕЛЬЗЯ до появления второго тенанта

- `tenantId` на всех доменных и дочерних таблицах;
- составные внешние ключи с тенантом;
- RLS и отдельная runtime-роль БД;
- разделение Account / Membership / Party;
- вынос прав из JWT;
- per-tenant уникальности;
- ресурсная модель календаря;
- аудит административных и privacy-действий.

Всё это меняет форму данных. Сделанное после второго тенанта — это миграция живых чужих данных,
а не своих.

## Порядок работ

**Шаг 1 — безопасность релиза (2–3 дня). ✅ ВЫПОЛНЕНО 2026-07-31 (`8886d40`)**
Упавшая миграция останавливает деплой; `JWT_SECRET` без запасного значения в проде.

**Шаг 2 — классификация.** Разметить все 98 моделей как GLOBAL / TENANT / TENANT_CHILD,
завести `Tenant(geleoteka)`, аддитивно добавлять `tenantId`.

**Шаг 3 — шов изоляции.** `withTenant`/`TenantTx`, отдельная runtime-роль БД,
негативные тесты на попытку межтенантного доступа по Deal/RepairOrder/Customer.

**Шаг 4 — идентичность.** Account / AuthIdentity / Session / TenantMembership и
Party / TenantCustomer / TenantSupplier рядом с работающим `User` через `LegacyUserMap`.

**Шаг 5 — права.** Каталог разрешений и `requirePermission` как фасад совместимости.
Все новые фичи пишутся только через него, чтобы долг `requireRole` перестал расти.

Фазы миграции: expand → dual-write/backfill → переключение чтения → включение RLS → contract.

## Находки, не связанные с мультитенантом (закрыть отдельно)

- **Фото машин клиентов отдаются без авторизации** — тот же маршрут, что публичный каталог,
  с заголовком «кэшировать вечно, публично». Защита только в неугадываемости идентификатора.
- **Подтверждения email нет вообще**, при том что email — основной идентификатор входа.
- **Аудита действий администратора нет** — кто и когда стёр клиента, восстановить нечем.
- Таблицы расписания и команды, заведённые 2026-07-30, тоже не имеют `tenantId`.

## Решение владельца (01.09.2026)

Вопрос об объёме закрыт: **полный объём сразу** — вариант 1. Рекомендация автора плана была
иной (вариант 2, изоляция сейчас и идентичность следом); владелец выбрал полный объём. Довод
владельца последователен с исходной постановкой: строим SaaS уровня продукта, а не сайт одного
сервиса, и полумера здесь означает вторую переделку.

**Второй сервис ожидается через полгода–год.** Это и есть срок, к которому платформа обязана
быть готова принимать чужие боевые данные.

**Порядок — параллельно с фундаментом мобильного API**
(`docs/plans/2026-09-01-mobile-api-foundation.md`), и это не конкурирующая линия, а часть той
же работы: API приложений требует ровно того, что дают шаги 4–5 — тенант в токене, права не из
токена, серверная проверка разрешений. Фундамент API становится первым потребителем новой
модели и её живой проверкой: если разрешения нельзя выразить в мобильном эндпоинте, значит
модель разрешений неверна, и это выясняется на второй неделе, а не через три месяца.

### Что это означает для продуктовых историй

Магазинные истории из `docs/prd/2026-09-01-bazon-gaps.md` (прайс из файла, площадки, ссылки
клиенту, калькулятор, оплата) **ждут**. Это прямое следствие выбора: полный объём означает,
что продуктовая разработка почти останавливается, и в исходном плане это было названо ценой
варианта 1. Уже выкаченное — себестоимость с ввозом, б/у запчасти, SEO — работает и не
трогается.

Исключение одно: если по ходу выяснится, что какая-то из историй нужна Гелеотеке как боевому
сервису прямо сейчас, она делается **через новый фасад разрешений**, а не в обход — иначе долг
`requireRole` начнёт расти обратно.

### Оговорка про сроки

Оценка 144–210 инженерных дней дана для команды из трёх инженеров с QA (14–18 календарных
недель). В нашем режиме работы календарный срок другой, и предсказать его честно я не могу.
Поэтому работа режется на вехи с проверяемым результатом, а не идёт единым куском:

| Веха | Проверяемый результат |
|---|---|
| Классификация моделей | все модели размечены GLOBAL / TENANT / TENANT_CHILD, заведён `Tenant(geleoteka)` |
| `tenantId` аддитивно | колонки и составные ключи есть, старый код работает как раньше |
| Шов изоляции | негативный тест: запрос с чужим тенантом не отдаёт ни строки |
| RLS и runtime-роль | забытый `WHERE` перестаёт быть инцидентом — доказывается тестом, а не обещанием |
| Идентичность | Account / AuthIdentity / Session / TenantMembership рядом с `User` через `LegacyUserMap` |
| Разрешения | `requirePermission` работает, мобильный эндпоинт ходит только через него |
| Второй тенант | подставной второй сервис заводится настройками и не видит данных первого |

Веха «второй тенант» — это и есть критерий готовности продукта из PRD: вторая установка
заводится настройками, без правки кода.

## Исходная развилка (сохранена для истории)

Оценка 144–210 дней — это цена «как правильно» целиком. Возможные рамки:

1. **Полный объём сразу** — платформа готова к второму тенанту, продуктовые фичи почти
   останавливаются на 3–4 месяца. ← **выбрано владельцем 01.09.2026**
2. **Шаги 1–3 сейчас, 4–5 следом** — изоляция данных появляется рано, разработка продолжается,
   разделение идентичности делается позже, но до второго тенанта.
3. **Только шаг 1 + правило «новые фичи через фасад»** — долг перестаёт расти, переделка
   откладывается осознанно.

Рекомендация автора плана была: **вариант 2**. Изоляция данных — то, что дороже всего чинить
задним числом и что нельзя доделать после прихода чужих данных; разделение идентичности
болезненно, но локально и переносит срок без роста риска.
