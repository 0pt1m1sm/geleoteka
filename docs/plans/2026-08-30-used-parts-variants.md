## Контекст (разведка 2026-08-30, проверено по коду и прод-базе)

**Блокер:** `Part.article @unique` (`prisma/schema.prisma:1132`) + отсутствие поля состояния → на один OEM-номер нельзя завести новую и б/у позицию.

**Почему варианты, а не сущность «экземпляр»:** экземпляр с количеством всегда 1 неотличим от товара с остатком 1; вторая личность потребовала бы протянуть новый идентификатор через корзину, `PartOrderItem`, `EstimateLine`, `StockItem`, резервы и `SupplierOrderItem` плюс переучить количественное ядро WMS. Проверка владельца по четырём критериям (комиссия / залог / гарантия на единицу / место на полке) — ни один не требует второй сущности; место на полке уже даёт `StockBin` за строкой остатка.

**Что уже готово и НЕ трогаем:**
- `PartReference.parts Part[]` — связь 1:N существует, множественность в комментарии схемы названа нормой.
- `StockItem` (partId, warehouseId, quantity, reserved) — количественная модель; б/у экземпляр = строка с остатком 1, резерв уже исключает двойную продажу.
- `StockBin` (itemId, warehouseId, location, quantity) + `StockBinMovement` — место на полке за каждым экземпляром без правок.
- `EstimateLine` уже несёт и `partId`, и `referenceId`.

**Состояние прод-базы на старте:** 70 товаров (69 активных, 56 с `referenceId`), 488 позиций справочника, **0 строк `PartOrderItem`**, 7 занятых ячеек. Миграция безопасна именно сейчас — с первой продажей появляются связи `Restrict`.

**Ограничения:**
- Конвенции `.claude/rules/geleoteka-conventions.md` обязательны (Prisma-типы явными аннотациями, клиент из `@/app/generated/prisma/client`, `useSyncExternalStore` с кэшем, CSS-переменные, `getSession()` + `redirect()`).
- Next.js версии проекта отличается от общеизвестной — перед кодом читать гайд в `node_modules/next/dist/docs/`.
- Миграции на проде накатываются сами при старте (`npm start`), отдельного шага деплоя нет.
- Гейт перед каждым PR: `npx tsc --noEmit`, `npm test` (базовая линия 612/612), `npm run lint` (0 ошибок, 4 предсуществующих предупреждения), `npm run build`. В `main` не пушить — только PR; мерж = автодеплой в прод.

## Implementation Tasks

### Story 1: Схема, генерация SKU и миграция каталога

**Status: VERIFIED** — PR #96 смержен 31.08 (7 коммитов, 3 круга ревью: code-reviewer, security-reviewer, verifier). Гейт зелёный целиком, CI зелёный, миграция проверена на чистой базе и на копии прод-данных с враждебными строками, вердикт независимой верификации — готово к мержу.

**Objective.** Снять блокер множественности и дать товару состояние, не сломав существующие 70 позиций.

**Изменения схемы** (`prisma/schema.prisma`, модель `Part` ~1128):
- `article` теряет `@unique`, индекс `@@index([article])` сохраняется — это OEM-номер, общий у нового и б/у.
- `sku String @unique` — торговый идентификатор. Для нового: равен артикулу. Для б/у: артикул + суффикс `-U1`, `-U2`, … (первый свободный).
- `condition PartCondition @default(NEW)` — новый enum `NEW | USED | REFURBISHED`.
- `conditionNote String?` — заметка о состоянии, показывается клиенту.
- `originNote String?` — происхождение: с какой машины снято и пробег. Информационный текст, НЕ связь с каталогом кузовов.

**Миграция.** Колонку `sku` добавить nullable → заполнить значением `article` для всех строк → перевести в NOT NULL и навесить уникальный индекс. Порядок обязателен: навесить unique до backfill нельзя. `condition` заполняется дефолтом `NEW`.

**Хелпер генерации.** `nextUsedSku(article, existingSkus)` в `lib/` — нормализация артикула, поиск первого свободного суффикса, устойчивость к дырам в нумерации (есть `-U1` и `-U3` → выдать `-U2` либо `-U4`, поведение зафиксировать тестом).

**Files.** `prisma/schema.prisma`, `prisma/migrations/20260830210000_part_variants/migration.sql`, `lib/part-sku.ts` (новый), `tests/parts/part-sku.test.ts` (новый).

**ИНВАРИАНТ, который нельзя откатывать (два круга ревью).** Защита от дубля обязана проверять ОБА ключа: `where: { OR: [{ article, condition: "NEW" }, { sku }] }`. По `article` — потому что миграция залила `sku` дословно, и для артикулов с пунктуацией (15 из 70 позиций прода) нормализованный ключ не совпадает с сохранённым. По `sku` — потому что уникальный индекс стоит именно на нём: иначе «A463-421-0098» и «A4634210098» пройдут проверку по тексту, а вставка упадёт необработанным P2002, а на легаси-строках вместо ошибки появится тихий дубль. Проверка одного ключа ломается в одну или другую сторону — это уже случалось дважды в этом PR. Места: `app/actions/parts.ts`, `app/actions/supplier-orders.ts`, `app/api/parts/import/route.ts`.

**Сделано сверх плана по итогам ревью:** `npm start` переведён с `&` на `;` — приложение больше не начинает обслуживать трафик параллельно с миграцией (иначе клиент Prisma, собранный по новой схеме, отдавал бы 500 на каждый запрос к `Part`, пока миграция не доехала); `&&` намеренно НЕ используем — по истории проекта `prisma migrate deploy` умеет выходить ненулевым кодом на предупреждениях и блокировал старт. `conditionNote`/`originNote` ограничены по длине (1000/500) — они уходят в SSR-HTML и JSON-LD каждой карточки. `DROP INDEX` получил `IF EXISTS`. `lib/seo-jsonld.ts` публикует `sku` вместо `article` — иначе два варианта одной детали отдали бы одинаковый sku, и Google схлопнул бы карточки; **добавлено поле `mpn`** с OEM-номером в исходном виде, но НЕ для служебных кодов (`SERVICE_ARTICLE_RE`): «ПОДЗАКАЗ-07» не является номером производителя, а на проде это 21 активная страница. **Инвариант «один НОВЫЙ товар на артикул» теперь держит база** — частичный уникальный индекс `Part_article_new_uq` (`WHERE condition = 'NEW'`), сырым SQL по образцу `Part_photos_gin_idx`; проверено: второй NEW с тем же артикулом отвергается, два б/у проходят.

**DoD.** Миграция применяется на чистой базе и на копии прод-данных; 70 товаров получают `condition=NEW` и `sku=article`; unit-тесты генерации SKU зелёные (включая дыры в нумерации и регистр); полный гейт зелёный.

**Поправка к DoD (независимая верификация).** Пункт «ни одного изменения поведения витрины» выполнен НЕ полностью и это принято осознанно: микроразметка каждой карточки получила новое поле `mpn`. Изменение аддитивное, значение `sku` для существующих товаров не поменялось (backfill дословный), служебные коды из `mpn` исключены. Прочее публичное поведение не менялось.

**Остаточная дыра, не закрытая Story 1** (обнаружена верификацией, на `main` вела себя так же): легаси-строка хранит sku дословно (`MANN-C29028`); если ту же деталь завести как `MANN C29028`, ветка по article не совпадёт (сравнение точное), нормализованный sku `MANNC29028` тоже не совпадёт, и появится тихий дубль. `Part_article_new_uq` этого не ловит — там article тоже сравнивается точно. Полное решение — нормализованная колонка-ключ; это отдельная инициатива, не Story 1.

### Story 2: Заведение б/у в админке

**Objective.** Менеджер заводит деталь с разбора за один проход, не думая про SKU.

**ОБЯЗАТЕЛЬНО ДО ПОЯВЛЕНИЯ ПЕРВОГО Б/У ТОВАРА (найдено двумя ревью Story 1, PR #96).**

**(а) Этикетки и резолверы сканирования.** Story 1 сняла гарантию «один товар = один артикул», на которую молча опирался весь складской контур. Хуже того: `app/(admin)/admin/warehouse/labels/page.tsx:62` печатает в QR `PART:<article>` — значит у нового товара и у б/у экземпляра одной детали этикетки **побайтово одинаковые**, различить их на складе физически нечем. Резолверы — `lib/warehouse/scan-router.ts:168`, `app/api/warehouse/scan/route.ts`, `app/actions/picking.ts`, `app/actions/packing.ts`, `app/actions/stocktake.ts` (две точки), `app/actions/supplier-orders.ts` (`receiveByCode`), `app/api/stock/lookup/route.ts` — везде `findFirst({ where: { article } })` без `orderBy`. Postgres вернёт произвольную строку, и порядок меняется после любого UPDATE. Последствие: подбор списывает остаток с чужой позиции, инвентаризация кладёт ADJUSTMENT не туда, приёмка засчитывается в чужую строку заказа, клиенту уходит б/у по цене новой. Фильтр `isActive: true` не спасает — б/у экземпляр активен. Печатать и резолвить надо по `sku` (он для того и заведён); при нескольких совпадениях по article — возвращать «неоднозначный код», а не первую строку.

**(б) `take: 1` в справочнике.** `app/actions/part-references.ts:60` берёт `parts: { select: { id: true }, take: 1 }` без `orderBy` и без фильтра по состоянию. Потребители ломаются предсказуемо: `components/admin/PartRefPicker.tsx` считает позицию занятой (`shopPartId !== null`) и **заблокирует создание нового товара из номенклатуры, у которой есть б/у экземпляр** — то есть сломает саму фичу; `components/crm/EstimatePartPicker.tsx` по тому же признаку уберёт позицию из автокомплита сметы; ссылка «уже в магазине» поведёт на случайный вариант. Нужен `condition: "NEW"` плюс решение, что показывать, когда нового товара нет, а б/у есть.

**(в) Retry на вставке.** Вставку б/у обязательно оборачивать в retry по `P2002` на `Part_sku_key` — `nextUsedSku` читает и считает неатомарно (докблок в `lib/part-sku.ts`). `createPart` сейчас не оборачивает транзакцию в try/catch, поэтому гонка вылезет 500-й, а не повтором.

**Хвост от верификации Story 1 (не блокер, но сделать здесь).** Тесты сторожат хелпер `duplicateNewPartWhere`, а не то, что вызывающие им пользуются: мутация «вписать `where: { sku }` прямо в вызове» проходит гейт зелёной. Сейчас это компенсирует индекс `Part_article_new_uq` (откат превращается в перехваченный P2002), но когда появится генерация б/у, нужен тест, реально дёргающий путь заведения товара.

**Задачи.**
- Форма создания и редактирования товара (`app/(admin)/admin/parts/new`, `[id]`): выбор состояния, поля заметки и происхождения; при состоянии «б/у» SKU генерируется автоматически и показывается только для чтения; остаток по умолчанию 1.
- Карточка позиции справочника (`app/(admin)/admin/parts/refs/[id]`) — кнопка «Добавить б/у экземпляр» с предзаполненными артикулом и названием; в списке связанных товаров видно состояние.
- Список товаров (`app/(admin)/admin/parts`): фильтр по состоянию, группировка по номенклатуре.
- Серверные действия — валидация: `condition=USED` требует хотя бы одного фото (это доказательство при гарантийном возврате) и непустой заметки.

**Files.** `app/(admin)/admin/parts/**`, `app/actions/parts.ts`, компоненты в `components/admin/`.

**DoD.** Три б/у экземпляра одной номенклатуры заводятся и получают разные SKU, фото и цены; валидация не пускает б/у без фото и заметки; фильтр и группировка работают; гейт зелёный.

### Story 3: Варианты на странице товара и в корзине

**Objective.** Покупатель видит выбор «новый / б/у» на одной странице и покупает б/у обычной кнопкой.

**Задачи.**
- `app/(public)/parts/[slug]/page.tsx` — блок вариантов: все активные товары той же номенклатуры (состояние, цена, остаток, фото, заметка, происхождение).

**Files.** `app/(public)/parts/**`, `components/parts/**`, `lib/parts-cart-store.ts`, тесты корзины.

### Story 4: Снятие проданного б/у с витрины

**Objective.** Проданный экземпляр исчезает с витрины, но остаётся в базе как факт продажи.

**Задачи.** При уходе остатка `USED`-товара в ноль (отгрузка/списание) выставлять `isActive = false`. Точку врезки выбрать там, где уже фиксируется движение остатка, чтобы не появилось второго источника правды. Строку товара не удалять — на неё ссылается `PartOrderItem` с `Restrict`.

**Files.** `app/actions/` (обработка заказа/отгрузки), `lib/warehouse/`, тесты.

**DoD.** Продажа последнего б/у экземпляра убирает его из витрины и из карты сайта; строка товара и строка заказа целы; новый товар с нулевым остатком НЕ гасится (он пополняемый); поведение покрыто тестом; гейт зелёный.

### Story 6: Страница по номеру детали и заявки о поступлении

**Objective.** Дать долговечный адрес и перестать терять горячий трафик.

**Задачи.**

- При отсутствии активных вариантов — форма «сообщить о поступлении».
- **Заявки держать в минимуме:** модель с контактом и ссылкой на номенклатуру, запись из формы, список в админке. НИКАКИХ автоуведомлений при появлении остатка — отдельная история на будущее.
