## Зачем этот файл отдельно

В архитектурном плане описано «что и почему»; здесь — «где мы сейчас». Он ведётся как
журнал: одна история = один проверяемый результат, отметка ставится только после выката и
проверки на проде. Файл переживает перезапуск сессии: чтобы продолжить, достаточно найти
первую непроставленную галочку.

## Правила на весь период

- **Только аддитивные изменения схемы.** Прод живой, в базе история трёх реальных клиентов.
  Порядок фаз: expand → dual-write/backfill → переключение чтения → включение RLS → contract.
  Ни одного `DROP` до последней фазы.
- **Каждый сторож проверяется мутантом** до коммита: сломать защищаемое свойство и убедиться,
  что тест краснеет. Зелёный тест без мутанта проверкой не считается.
- **Новая функциональность — только через фасад разрешений.** Долг `requireRole` (~186 мест)
  не должен расти.
- Гейт перед каждым PR: `npx tsc --noEmit`, `npm test`, `npm run lint`, `npm run build`.
  Мерж в main = автодеплой; миграции накатываются сами при старте.

## Implementation Tasks

### Story 1: Классификация моделей и сторож на неклассифицированные

**Цель.** У каждой из 79 моделей записан класс — GLOBAL / TENANT / TENANT_CHILD — и появление
новой модели без класса роняет тесты. Без этого следующие истории будут спорить о том, куда
класть `tenantId`, на каждой таблице отдельно.

**Файлы.** `lib/tenant/model-classification.ts` (новый), `tests/tenant/classification.test.ts`.

**Готово, когда:**
- классы объявлены для всех моделей схемы, у неочевидных — причина одной строкой;
- сторож читает `prisma/schema.prisma` и падает, если модель не классифицирована или
  классифицирована несуществующая;
- TENANT_CHILD обязан называть родителя, через которого наследует аренду, и родитель обязан
  быть TENANT или TENANT_CHILD — цепочка не может начинаться с GLOBAL;
- сторож проверен мутантом.

### Story 2: Модель `Tenant` и запись «geleoteka»

**Цель.** Появляется сущность арендатора; текущая установка — первая её строка.

**Готово, когда:** модель `Tenant` (ключ, название, статус, создан), миграция аддитивная,
запись `geleoteka` заводится идемпотентно (сидом и миграцией данных), `lib/tenant.ts`
отдаёт ключ из неё, а не из константы. Старый код продолжает работать.

### Story 3: `tenantId` аддитивно на корневых сущностях

**Готово, когда:** у всех TENANT-моделей есть `tenantId` (nullable на время фазы expand),
backfill проставил его существующим строкам, запись новых строк проставляет его всегда.
Ни одного обязательного поля до фазы переключения чтения.

### Story 4: `tenantId` на дочерних + составные ключи

**Готово, когда:** TENANT_CHILD получают `tenantId`, внешние ключи становятся составными
(родитель + тенант), и база отказывается связать строку с родителем чужого тенанта.

### Story 5: Шов изоляции `withTenant` и негативные тесты

**Готово, когда:** есть единая точка входа в данные, знающая тенанта; негативный тест
доказывает, что запрос с чужим тенантом не отдаёт ни строки по Deal, RepairOrder и клиенту.

### Story 6: Перевод чтений на шов

**Готово, когда:** доменные чтения идут через шов; прямые обращения к `db` вне шва
перечислены и обоснованы.

### Story 7: RLS и отдельная runtime-роль БД

**Готово, когда:** политики включены, приложение ходит под ролью без BYPASSRLS, и тест
доказывает: забытый `WHERE` не отдаёт чужие строки.

### Story 8: Каталог разрешений вместо ролей

**Готово, когда:** каталог разрешений объявлен, `requirePermission` работает поверх него,
новые точки входа не используют `requireRole`, а долг зафиксирован числом.

### Story 9: Идентичность — Account / AuthIdentity / Membership

**Готово, когда:** таблицы заведены рядом с работающим `User` через отображение, вход идёт
через них за флагом, и три цели поглощённого плана выполнены: управление учёткой в админке,
смена логина отдельно от контактов CRM, слияние дублей клиентов.

### Story 10: Per-tenant уникальности и счётчики нумерации

**Готово, когда:** глобальные уникальности (email, номера документов, коды) становятся
составными с тенантом; нумерация идёт от счётчика тенанта.

### Story 11: Подставной второй тенант — доказательство изоляции

**Готово, когда:** второй тенант заводится настройками, наполняется данными и не видит
данных первого — ни через приложение, ни прямым запросом под runtime-ролью. Это же критерий
готовности продукта из PRD.
