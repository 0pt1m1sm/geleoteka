## Зачем

Приложений два, а API нет ни одного. В коде 164 экспортированных серверных действия и 26
роутов — почти все внутренние (выгрузки, вебхуки, счётчики бейджей). Серверное действие из
приложения вызвать нельзя: это не HTTP-контракт, а внутренний механизм фреймворка с
собственным форматом запроса, который меняется от версии к версии.

## Почему это отдельная спецификация, а не часть приложения

Обоим приложениям нужен один и тот же фундамент: вход, обновление токена, права, определение
сервиса, формат ошибок, версия. Если написать его дважды, разойдутся — а разошедшийся API
нельзя починить одним деплоем, потому что старая версия приложения останется у людей на
телефонах.

## Что нельзя сделать задним числом

Веб мы деплоим синхронно: сервер и клиент обновляются вместе. **Приложение из App Store так не
работает.** Установленная версия живёт месяцами, а у части пользователей — годами. Отсюда три
свойства, которые закладываются сразу и не переделываются:

1. **Версия в пути** (`/api/mobile/v1/...`). Ломающее изменение — это `v2` рядом, а не правка
   `v1`. Иначе первое же изменение контракта превращает установленные приложения в кирпич.
2. **Тенант в токене.** Владелец 01.09 выбрал полный объём мультиарендности, и эта работа
   идёт параллельно, поэтому в токене окажется настоящий идентификатор тенанта, а не заглушка
   поверх константы `lib/tenant.ts`. Даже если бы объём был меньше, поле закладывалось бы с
   первого дня: токен, выпущенный сегодня, предъявляется через полгода, и добавить в него поле
   задним числом — значит разослать обновление и разлогинить всех, у кого оно не установилось.
3. **Права не из токена.** Сейчас `permissionRole` едет в JWT и ему верят. Для веба это
   исправимо в любой день; для приложения — нет: понижение роли сотрудника не подействует,
   пока он не перезайдёт. Права проверяются на сервере по текущему состоянию.

Это ровно тот же довод, что в плане мультиарендности про «нельзя откладывать до второго
тенанта», только резче: там нельзя мигрировать чужие данные, здесь — чужие телефоны.

### Story 1: Токены для приложения

**Цель.** Вход из приложения без cookie, с возможностью отозвать доступ.

**Файлы.** `lib/auth.ts` (чтение токена из заголовка), `lib/auth/mobile-tokens.ts` (новый),
`app/api/mobile/v1/auth/*` (вход, обновление, выход), тесты.

**Готово, когда:**
- вход отдаёт короткий access-токен и долгий refresh; refresh хранится хешем в базе, а не
  выдаётся навсегда;
- `getSession()` принимает и cookie (веб), и `Authorization: Bearer` (приложение) — одна
  функция, а не две реализации сессии;
- существующий отзыв всех сессий (`sessionsRevokedAt` + `iat`) действует и на мобильные
  токены: тест на «сменил пароль → приложение разлогинилось»;
- выход из приложения гасит именно свой refresh, а не все устройства;
- refresh одноразовый: повторное использование гасит цепочку (признак кражи токена);
- тест-мутант: снятие проверки отзыва роняет тест.

**Осознанно не делаем.** Биометрию и хранение пароля — токен лежит в защищённом хранилище
устройства (Keychain), пароль в приложении не хранится вовсе.

### Story 2: Каркас API

**Цель.** Один способ отвечать, ошибаться и ограничивать — до того, как появятся десятки
эндпоинтов.

**Файлы.** `lib/api/mobile/handler.ts`, `lib/api/mobile/errors.ts`, `lib/api/mobile/schema.ts`,
тесты.

**Готово, когда:**
- обёртка обработчика: разбор токена, проверка разрешения, валидация тела, единый формат
  ошибки (код, человеческий текст, поле) — приложение показывает текст, а не «Error 500»;
- минимальная поддерживаемая версия приложения: сервер умеет ответить «обновите приложение»
  осмысленной ошибкой, а не сломанным разбором;
- троттлинг по учётной записи и устройству переиспользует `lib/rate-limit.ts`;
- ошибки не текут наружу: внутреннее исключение не превращается в текст для пользователя;
- ответы курсорные, без `offset`: список заказов на телефоне листают, а не нумеруют.

### Story 3: Тенант и брендирование

**Цель.** Одно приложение обслуживает много сервисов.

**Готово, когда:**
- токен несёт тенанта; каждый запрос читает его из токена, а не из тела запроса;
- эндпоинт брендирования отдаёт приложению название сервиса, логотип, цвета, контакты и
  включённые модули (магазин, аренда, склад) — приложение рисует то, что сервис купил;
- негативный тест: токен одного сервиса не читает данные другого. Пока тенант один, тест
  ставится на подставном втором — иначе проверять будет нечего до самого прихода клиента;
- ничего специфичного для Гелеотеки в коде приложения и API нет — проверяется поиском по
  строкам при сборке.

### Story 4: Разрешения вместо ролей

**Цель.** Не тащить в приложение долг `requireRole`, которого в коде под две сотни мест.

**Готово, когда:**
- мобильные эндпоинты ходят через фасад разрешений (`requirePermission`) из плана
  мультиарендности, а не через `requireRole` напрямую;
- поскольку мультиарендность делается полным объёмом, фасад к этому моменту — настоящий
  каталог разрешений, а не отображение в старые роли; мобильный эндпоинт становится его первым
  потребителем и живой проверкой: разрешение, которое нельзя выразить в эндпоинте, — признак
  неверной модели, и лучше узнать это на второй неделе, чем через три месяца;
- приложение получает список своих разрешений и прячет то, чего нельзя, но сервер всё равно
  проверяет: спрятанная кнопка — не защита.

### Story 5: Загрузка файлов и фотографий

**Цель.** Фотографии приёмки и дефектов с телефона.

**Готово, когда:**
- загрузка через существующий механизм (`app/api/upload`), но с токеном и лимитом размера;
- изображение ужимается на устройстве до отправки — иначе приёмка по мобильной сети встанет;
- приватные фотографии отдаются с проверкой доступа. В плане мультиарендности отмечено, что
  фотографии машин клиентов сейчас доступны без авторизации по неугадываемой ссылке — API
  приложения не должен закреплять эту практику.

## Риски

**Второй способ делать то же самое.** API легко превращается во вторую реализацию бизнес-логики,
и тогда веб и приложение начинают вести себя по-разному. Смягчение: эндпоинт вызывает ту же
функцию из `lib/`, что и серверное действие. Если логика лежит внутри действия — она сначала
выносится в `lib/`, и только потом вызывается из обоих мест.

## Проверка

Гейт полностью. Плюс: коллекция запросов, прогоняемая против локального сервера, — вход,
обновление токена, отзыв, чужой тенант, просроченная версия приложения.
