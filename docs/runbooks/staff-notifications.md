# Уведомления сотрудников: canary и аварийное отключение

## Транспорт: почему polling, а не webhook

РКН замедляет трафик Telegram↔РФ (официально с февраля 2026). Webhook требует,
чтобы Telegram дозвонился ДО нашего сервера в РФ: соединения таймаутят,
Telegram удваивает интервалы ретраев, апдейты приходят с опозданием в минуты.
Поэтому приём идёт опросом `getUpdates`: мы сами забираем обновления, входящая
достижимость сервера не участвует вовсе. **Регистрировать webhook не нужно.**
Если webhook когда-то был зарегистрирован, первый же опрос получит 409, сам
вызовет `deleteWebhook` (не сбрасывая накопленные апдейты) и продолжит.

Опрос запускается: (а) каждым тиком `staff-notifications-dispatch-cron`
(maintenance-endpoint), (б) автоматически каждые ~5 секунд, пока сотрудник
ждёт привязку на странице профиля. Подтверждение привязки читается из НАШЕЙ
базы — панель показывает «Привязка выполнена», как только строка закоммичена;
ответ бота в чате — только вежливость и может запаздывать.

## Медленный канал: релей вне РФ (опционально, но рекомендуется)

Исходящие вызовы к `api.telegram.org` из РФ перемежаются: часть проходит за
сотни миллисекунд, часть висит до таймаута. Замеры видны на
`/admin/notifications/operations` (операция «Опрос обновлений» и отправки).
Если доля отказов мешает, поставьте релей вне России и укажите его в настройке
`TELEGRAM_API_BASE_URL` — через него пойдут и отправка, и приём.

Минимальный релей — Cloudflare Worker (бесплатного тарифа достаточно):

```js
export default {
  async fetch(request) {
    const url = new URL(request.url);
    url.hostname = "api.telegram.org";
    url.protocol = "https:";
    url.port = "";
    return fetch(new Request(url, request));
  },
};
```

Задеплоить (`wrangler deploy` или через дашборд), адрес вида
`https://<имя>.<аккаунт>.workers.dev` вписать в `TELEGRAM_API_BASE_URL`.
Worker не хранит и не логирует токен — он только проксирует путь, в котором
токен уже содержится, поэтому адрес релея надо беречь так же, как сам токен.

## Перед включением

1. В `/admin/settings/integrations` заполнить: `TELEGRAM_BOT_TOKEN`,
   `TELEGRAM_BOT_USERNAME`, Bearer-секрет cron и
   `STAFF_NOTIFICATION_RETENTION_DAYS` (разумная отправная точка — 90 дней).
   `TELEGRAM_WEBHOOK_SECRET` НЕ нужен; `TELEGRAM_API_BASE_URL` — по желанию
   (см. релей выше).
2. Оставить `TELEGRAM_ENABLED=false`, включить только нужные `TELEGRAM_NOTIFY_*`.
3. Проверить, что `staff-notifications-dispatch-cron` вызывает оба endpoint:
   maintenance и dispatch. HTTP 401/403/500/503 обязан красить workflow
   красным; код 000 означает сетевой обрыв и завершает только текущий tick.

## Canary

1. Переключить `TELEGRAM_ENABLED=true`. Сервер атомарно сохранит `TELEGRAM_ENABLED_AT`; события с `occurredAt` раньше этой отметки delivery-строк не получают.
2. Привязать личный Telegram одного тестового ADMIN: профиль → «Создать ссылку», отправить боту команду привязки (надёжнее скопировать и отправить вручную одним сообщением). Успех показывает САМА СТРАНИЦА в течение ~10–30 секунд; ответ бота в чате может запаздывать и признаком не является.
3. Нажать «Отправить тестовое уведомление» в профиле и посмотреть исход с длительностью.
4. Создать одно новое контролируемое событие разрешённого типа и проверить `/admin/notifications/operations`: событие опубликовано, delivery проходит `PENDING → SENT`, `DEAD` не растёт.
3. Привязать общий служебный fallback и повторить canary для события без владельца.
4. Только после этого подключать личные назначения остальных сотрудников и включать типы событий по одному.

## Эксплуатация

- `/admin/notifications/operations` доступен только с `notifications.manage`. Экран показывает количества по всем delivery-статусам, `PENDING/RETRY/DEAD`, тип события, попытки и только нормализованный `lastErrorCode`; PII, `destinationKey` и `chat_id` туда не выбираются.
- Ручной повтор доступен для `DEAD`: он переводит ту же delivery-строку в `PENDING`, сбрасывает попытки и пишет административное действие в `AuditLog`. Новое бизнес-событие не создаётся.
- Maintenance cron идемпотентно публикует просрочки и удаляет события старше настроенного retention. Receipts и deliveries удаляются по `ON DELETE CASCADE`.

## Отключение одним переключателем

1. Установить `TELEGRAM_ENABLED=false` в интеграциях.
2. Та же транзакция переводит все активные Telegram-deliveries (`PENDING/PROCESSING/RETRY`) в `CANCELLED` и удаляет отметку текущей эпохи включения. Проектор продолжает создавать внутренние receipts, но не создаёт Telegram-deliveries, поэтому очередь выключенного канала не растёт.
3. Адаптер перечитывает master switch перед каждым HTTP-вызовом. Уже начавшийся внешний запрос невозможно отозвать; после завершения этой единственной in-flight попытки новых отправок быть не должно.
4. При следующем включении будет создан новый `TELEGRAM_ENABLED_AT`. Старые события и deliveries предыдущей эпохи не рассылаются.

Если канал мешает, сначала выключить master switch, затем смотреть `CANCELLED/DEAD` и коды ошибок. Не удалять события вручную и не менять `chat_id` SQL-командами.
